=====================================================
BLOCKER
=====================================================

1. nik not null unique -> admin pemerintahan gabisa signup
-----------------------------------------------------
Drop the NOT NULL, keep the UNIQUE. Di Postgres NULL dianggap distinct,
jadi banyak baris ber-nik NULL tetap lolos unique constraint. Gaperlu
partial index.

Biar tetap ketat, nik cuma diwajibin buat role 'user':

  alter table users alter column nik drop not null;
  alter table users add constraint users_nik_required_for_citizen
    check (role <> 'user' or nik is not null);


2. role masih varchar, takut mismatch
-----------------------------------------------------
Pakai native enum:

  create type user_role as enum ('user', 'instansi', 'super_admin');

Catatan: samain penulisannya sekarang. 'super admin' (spasi) vs
'super_admin' (underscore) itu sumber mismatch paling gampang kejadian.
Trade-off enum: nambah value harus ALTER TYPE, value lama gabisa dihapus.
Alternatif varchar + check lebih gampang diubah tapi gabisa dipake sebagai
tipe kolom di tabel lain.


3. users belum punya agency_id  <- ini blocker yang sebenernya
-----------------------------------------------------
Role 'instansi' harus tau dia pegang agency yang mana. Tanpa kolom ini
dashboard gabisa nge-filter queues/counters punya siapa.

  agency_id bigint references agencies (id) on delete restrict
  check ((role = 'instansi') = (agency_id is not null))

Efek check-nya: instansi wajib punya agency, user & super_admin wajib null.
Super admin jadi global scope (belum diputusin, lihat open question).


4. agencies tetap dipertahanin  <- keputusan berubah dari catatan awal
-----------------------------------------------------
Rencana awal: hapus agencies, cukup andelin role di users.
Keputusan akhir: JANGAN dihapus. Alasannya:

  - Lifecycle-nya beda. Akun itu kredensial (bisa di-reset, dihapus pas
    offboarding). Agency itu entri direktori yang ditunjuk services,
    counters, dan semua queue history. Kalau digabung, cascade dari akun
    yang dihapus bakal ikut ngehapus katalog layanan + riwayat antrian.

  - users nyimpen NIK semua warga. Kalau identitas agency ditaruh di situ,
    query publik "browse services by agency" bakal join langsung ke tabel
    berisi PII. Jadi harus nulis RLS buat bikin jalur baca publik nembus
    tabel PII, permanen, cuma buat hemat satu tabel 3 kolom.
    Sekarang agencies aman dibuka read-only ke semua orang.

  - Atribut agency (desc, alamat, jam operasional, logo) bakal jadi kolom
    di users yang NULL buat semua baris warga.

Relasi agencies -> users itu ONE TO MANY, bukan one to one. FK-nya ada di
users, jadi banyak baris user boleh nunjuk agency yang sama. Gaada yang
maksa harus one-to-one.


5. Satu akun per agency (scope yang dipilih)
-----------------------------------------------------
Keputusan: semua pegawai di satu instansi (cth Dukcapil Surabaya) share
1 akun login.

Cara implementasinya BUKAN dengan ngehapus agencies, tapi cukup jangan
pernah bikin baris 'instansi' kedua buat agency yang sama. Kalau mau
dipaksain sama DB:

  create unique index users_one_account_per_agency
    on users (agency_id)
    where role = 'instansi';

Partial unique index, jadi cuma ngiket baris instansi. Warga (agency_id
null semua) gak kena.

Kalau nanti berubah pikiran mau akun per pegawai: tinggal DROP INDEX itu,
gaada perubahan skema lain. Ini alasan utama kenapa agencies gak digabung.


6. Auth: pakai Supabase Auth (dikonfirmasi)
-----------------------------------------------------
users.id = uuid, primary key SEKALIGUS foreign key ke auth.users(id).
Jadi users itu tabel profil yang mirror auth.users, relasinya one-to-one.
Semua FK yang nunjuk users (queues.user_id, family_members.user_id) ikut
bertipe uuid.

TODO: butuh trigger on insert di auth.users buat bikin baris profil, dan
trigger itu harus tau role apa yang di-assign. Warga self-signup jadi
'user'; akun instansi hampir pasti dibuatin super admin, jadi alurnya
beda. Diputusin dulu sebelum nulis trigger-nya.


7. queues bisa nyimpen kombinasi service + counter beda agency
-----------------------------------------------------
Agency bisa ditarik lewat dua jalur: service_id -> services.agency_id
dan counter_id -> counters.agency_id. Dua jalur ini bisa beda isinya dan
gaada yang nolak.

Solusi: composite FK. Tambah agency_id di queues (redundan, tapi bikin
mismatch mustahil di level DB).

  alter table services add constraint services_id_agency_key
    unique (id, agency_id);
  alter table counters add constraint counters_id_agency_key
    unique (id, agency_id);

  queues:
    foreign key (service_id, agency_id) references services (id, agency_id)
    foreign key (counter_id, agency_id) references counters (id, agency_id)

Kalau counter_id nullable, composite FK-nya ikut nullable. MATCH SIMPLE
bakal ngelewatin pengecekan pas counter_id NULL, jadi aman.


8. Index FK
-----------------------------------------------------
Postgres GAK bikin index otomatis buat kolom FK. Semua kolom (*) perlu
index manual, terutama queues.user_id / service_id / counter_id. Tanpa itu
delete di parent table jadi sequential scan.

Query dashboard kemungkinan besar filter by (agency, schedule_date,
status) -> siapin composite index sesuai pola query yang jadi nanti.


=====================================================
SKEMA HASIL AKHIR
=====================================================

create type user_role as enum ('user', 'instansi', 'super_admin');

create table agencies (
  id          bigint generated always as identity primary key,
  name        text not null,
  description text,
  created_at  timestamptz not null default now()
);

create table users (
  id         uuid primary key references auth.users (id) on delete cascade,
  nik        text unique,
  full_name  text not null,
  email      text not null unique,
  role       user_role not null,
  agency_id  bigint references agencies (id) on delete restrict,
  created_at timestamptz not null default now(),

  constraint users_nik_required_for_citizen
    check (role <> 'user' or nik is not null),
  constraint users_agency_matches_role
    check ((role = 'instansi') = (agency_id is not null))
);

create unique index users_one_account_per_agency
  on users (agency_id)
  where role = 'instansi';

create table services (
  id             bigint generated always as identity primary key,
  agency_id      bigint not null references agencies (id) on delete cascade,
  name           text not null,
  requirements   jsonb not null default '[]'::jsonb,
  estimated_time interval not null,

  constraint services_id_agency_key unique (id, agency_id)
);

create table counters (
  id           bigint generated always as identity primary key,
  agency_id    bigint not null references agencies (id) on delete cascade,
  counter_name text not null,
  status       text not null,

  constraint counters_id_agency_key unique (id, agency_id)
);

create table queues (
  id            bigint generated always as identity primary key,
  user_id       uuid   not null references users (id) on delete cascade,
  agency_id     bigint not null,
  service_id    bigint not null,
  counter_id    bigint,
  queue_number  int    not null,
  schedule_date date   not null,
  time_block    text   not null,
  status        text   not null,
  created_at    timestamptz not null default now(),

  constraint queues_service_fk
    foreign key (service_id, agency_id) references services (id, agency_id),
  constraint queues_counter_fk
    foreign key (counter_id, agency_id) references counters (id, agency_id)
);

create table family_members (
  id           bigint generated always as identity primary key,
  user_id      uuid not null references users (id) on delete cascade,
  nik          text not null,
  full_name    text not null,
  relationship text not null,
  created_at   timestamptz not null default now(),

  constraint family_members_user_nik_key unique (user_id, nik)
);

create index on users (agency_id);
create index on services (agency_id);
create index on counters (agency_id);
create index on queues (user_id);
create index on queues (service_id);
create index on queues (counter_id);
create index on queues (agency_id, schedule_date, status);
create index on family_members (user_id);
